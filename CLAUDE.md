# CLAUDE.md — Airlock engineering guide

This file governs how code gets written in this repository. It is not a style suggestion; treat every rule here as a review blocker. When a rule conflicts with speed, the rule wins — this project is judged on execution quality, and sloppy code is the most common way hackathon projects lose.

## 1. What we are building, in one paragraph

Airlock is a governance gateway between AI agents (MCP clients) and a SQL warehouse. It compiles policy from a DataHub instance (tags, glossary terms, lifecycle, domains, schemas, lineage), parses every incoming SQL query into an AST with sqlglot, resolves columns to catalog URNs, applies verdicts (allow / mask / deny / substitute), rewrites the query, executes it, and returns rows plus a machine-readable explanation envelope. Every decision is audited locally and written back to DataHub. Read `README.md` fully before writing any code; the README is the spec. If implementation reality forces a deviation from the README, update the README in the same PR — they must never drift.

## 2. The judging criteria are requirements, not context

We are building for "Build with DataHub: The Agent Hackathon" (https://datahub.devpost.com/). The judges score on:

1. **Use of DataHub** — must be meaningful; strong submissions write back to the graph. Our write-back ledger and structured properties are therefore *core scope*, not stretch scope. Never stub them out to save time.
2. **Technical execution** — "does the code do what the submission claims." Every feature named in the README must demonstrably work in the demo stack. If a feature can't be finished properly, remove it from the README rather than shipping it broken.
3. **Originality** — our originality is semantic enforcement + catalog-compiled policy + agent-readable verdicts. Protect these three; deprioritize everything else.
4. **Real-world usefulness** — bias every UX decision toward "would a platform engineer at Pinterest adopt this."
5. **Submission quality** — README, demo video, `examples/` folder with captured envelopes and before/after SQL. Keep `examples/` regenerated by `make examples` so it never goes stale.
6. **Bonus: open-source contribution to DataHub** — we ship our snapshot-refresh trigger as a proposed DataHub Action and file it upstream; keep that code cleanly separable in `contrib/`.

Submission hard requirements to never forget: public repo, **Apache 2.0 LICENSE visible in the repo root and in the GitHub About section**, sub-3-minute video, judge-runnable setup. `python demo/up.py` must work on a clean macOS, Linux, *and* Windows machine with only Docker and Python installed — verified in the CI matrix on every commit, never assumed. Judges run demos on whatever laptop they own; "works on my machine" is a losing submission.

## 3. Stack (pinned; do not substitute without an ADR)

- **Python 3.11+**, `uv` for env/deps, `pyproject.toml` only (no requirements.txt).
- **sqlglot** for parsing/qualification/rewriting. Before writing analyzer code, read: https://sqlglot.com/sqlglot.html and the AST primer at https://github.com/tobymao/sqlglot/blob/main/posts/ast_primer.md . Use `qualify` and scope traversal from `sqlglot.optimizer` — do not hand-roll alias resolution.
- **MCP Python SDK / FastMCP** for the server layer: https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/main/README.md . Protocol spec sitemap: https://modelcontextprotocol.io/sitemap.xml (fetch pages with `.md` suffix).
- **DataHub**: Python SDK (`acryl-datahub`) for snapshot compilation and write-back. Docs to consult: https://docs.datahub.com/docs/features/feature-guides/mcp , https://docs.datahub.com/docs/api/datahub-apis , https://docs.datahub.com/docs/metadata-modeling/metadata-model . Structured properties and documents are the write-back surfaces.
- **DuckDB** as the primary demo warehouse adapter; Postgres second. Snowflake only if time remains.
- **pydantic v2** for all boundary models; **pytest + hypothesis** for tests; **ruff** (lint + format) and **mypy --strict** in CI.
- **Typer** for the CLI; **rich** for `airlock tail` output.

When you need library usage details, fetch the official docs above rather than relying on memory — APIs drift, and a hallucinated kwarg in a security tool is unacceptable.

## 4. Repository layout

Follow the module layout in README §"Module layout (LLD)" exactly. Additional rules:

- `engine/decide.py` is **pure**: no I/O, no clock, no globals. `(ResolvedQuery, Principal, PolicyGraph) -> list[Verdict]`. This purity is what makes decisions replayable and testable; guard it jealously.
- `policy/compile.py` is the **only** module that talks to DataHub for reads. `audit/datahub_sink.py` is the only module that writes to it. Everything else consumes the `PolicyGraph` type.
- One warehouse adapter per file in `exec/`, all implementing the same `WarehouseAdapter` protocol. No adapter-specific logic outside `exec/`.
- `demo/` is self-contained: compose file, seed scripts, `SCRIPT.md`, agent config. Nothing in `airlock/` may import from `demo/`.

## 5. Nomenclature — the ubiquitous language

Use these words, exactly, everywhere (code, docs, log lines, commit messages). Inventing synonyms is how codebases rot.

| Term | Meaning | Never call it |
|---|---|---|
| `Principal` | An authenticated agent identity | user, client, caller, actor |
| `Rule` | A match+action pair in airlock.yaml | policy (a policy is the whole set) |
| `PolicyGraph` | Compiled, content-addressed snapshot of catalog facts + rules | cache, context, metadata |
| `Verdict` | One decision about one subject (column/table/statement) | result, outcome, finding |
| `ReasonCode` | Stable `AIRLOCK-NNN` identifier on every verdict/error | error code, status |
| `Envelope` | The structured MCP response (rows + verdicts + refs) | response, payload |
| `ResolvedQuery` | AST + every reference bound to a URN + classifications | parsed query |
| `Subject` | The thing a verdict is about (`column:...`, `table:...`) | target, entity |
| `Snapshot` | One immutable PolicyGraph version, addressed by hash | version, state |

Naming rules: functions are verbs (`resolve_columns`, `compile_snapshot`), not nouns (`column_resolver.run`). No `Manager`, `Handler`, `Helper`, `Util`, `Service`, or `Processor` class names — if you reach for one, the abstraction is wrong; name the thing by what it does. Reason codes are allocated in `engine/verdicts.py` in one table with a comment per code; never inline a bare `"AIRLOCK-123"` string elsewhere.

## 6. Anti-slop rules (how to not look AI-generated)

The tell of AI-generated code is not any single line — it's texture: over-commented, over-abstracted, over-hedged, weirdly generic. These rules remove the texture.

**Comments.** Comments explain *why*, never *what*. Delete any comment restating the code (`# increment counter`). A file should have a handful of load-bearing comments (invariants, gotchas, links to the edge-case table in the README), not a narration. No docstring boilerplate on private functions; public functions get one-to-three-line docstrings describing behavior and failure modes, no `Args:/Returns:` scaffolding unless the signature is genuinely non-obvious.

**No emoji anywhere in code, comments, log lines, or CLI output.** The demo aesthetic comes from `rich` tables and color, not sparkle.

**Abstraction budget.** No interfaces with one implementation (exception: `WarehouseAdapter`, which will have three). No config options nobody asked for. No `**kwargs` pass-throughs. Three similar lines do not need a helper; three similar *modules* do. Inline the trivial.

**Error handling.** Never `except Exception: pass`. Catch the narrowest exception you can name, at the boundary where you can do something about it, and convert it into a typed Airlock error with a ReasonCode. Internal errors crossing the MCP boundary become `AIRLOCK-4xx` envelopes with a request_id — the traceback goes to the log, never to the wire.

**Hedging.** No `# TODO: handle edge cases`, no `# this should probably...`, no defensive `if x is not None` walls where `x` cannot be None by type. If an edge case from README table §"Edge cases" is unhandled, the code raises `NotImplementedError` with the table row number — visible, honest, greppable — until it's handled.

**Dead weight.** No commented-out code, no unused imports (ruff enforces), no `utils.py` junk drawer, no example code left in `if __name__ == "__main__"` blocks outside `demo/`.

**Prose in the repo** (docs, README edits, PR descriptions): no marketing adjectives ("powerful", "seamless", "cutting-edge"), no "In this PR, we..." throat-clearing, no bullet lists of one item. Write like the sqlglot or DuckDB maintainers write: plain, specific, confident, short.

**Log lines** are events with fields, not sentences: `decision.made request_id=req_01J principal=growth-agent verdicts=3 latency_ms=4`. Use structlog conventions; never f-string interpolate values into the message key.

## 7. Robustness rules

- **Fail closed** is the default everywhere. Any code path that fails open must be reachable only via an explicit config value, and that config line must appear in README's configuration reference.
- **Every deny/mask/substitute carries a ReasonCode, a human reason, and at least one actionable hint.** A verdict without a hint is a review blocker.
- **Validate at the boundary, trust inside.** Pydantic models at MCP ingress, config load, and DataHub responses; internal code operates on validated types and does not re-check.
- **The edge-case table in the README is the test plan.** Every row gets at least one test named `test_edge_NN_<slug>`; CI fails if a row lacks one (enforced by a small script in `tools/check_edges.py`).
- **Property-based tests for the rewriter** (hypothesis): generate queries with nested CTEs/aliases/unions over a known schema; assert (a) every sensitive column in the output SQL is masked or absent, (b) rewritten SQL still parses in the target dialect, (c) non-sensitive columns are byte-identical. This suite is the project's crown jewel; budget real time for it.
- **Golden-file tests** for envelopes: captured request → expected envelope JSON, diffed exactly. Regenerate deliberately with `make golden`, never by hand-editing.
- **Snapshot immutability**: PolicyGraph objects are frozen dataclasses; the store swaps an atomic reference. Any mutation attempt should raise.
- **No network in unit tests.** DataHub and warehouses are faked behind their protocols; integration tests run against the demo compose stack in a separate CI job.
- **Performance budget in CI**: parse+decide+rewrite p95 < 10ms on the benchmark corpus (`make bench`); regressions fail the build.

## 8. MCP server quality bar

(Distilled from the MCP best-practices guidance; verify details against the spec links in §3.)

- Tool names are prefixed and action-oriented: `warehouse_run_query`, `warehouse_list_tables`, `warehouse_describe_table`. Descriptions are one tight paragraph including when *not* to use the tool.
- Define input schemas with pydantic and output schemas via `structuredContent` so clients get typed envelopes, not prose.
- Annotate honestly: `readOnlyHint: true` on all three tools (Airlock is read-only in v1); `openWorldHint: false`.
- Errors returned to the agent must be *actionable for an agent*: state what to change in the next call. Test this literally — our eval suite (below) includes "agent receives deny, reformulates successfully."
- Test with MCP Inspector (`npx @modelcontextprotocol/inspector`) before every demo recording.
- Build an eval set of 10 realistic questions against the demo catalog (mix of clean, maskable, deniable, substitutable) with verified expected envelopes; run it as `make eval`. This doubles as the demo rehearsal.

## 9. Git & process hygiene

- Conventional commits (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`); imperative mood; body explains *why* when non-obvious. No `wip`, no `misc fixes`.
- Small PRs, one concern each. Every PR: tests for new behavior, README updated if behavior is user-visible, `ruff` + `mypy` clean.
- Architecture decisions that pin or reverse something in this file go in `docs/adr/NNN-title.md` (context → decision → consequences, one page max).
- Never commit secrets, tokens, or `.env`; demo credentials live in `demo/.env.example` with obviously fake values.

## 10. Real by construction — no mocks, DataHub compulsory

- **The product never mocks.** No `--mock`, no `--demo` bypass, no fixture policy files loadable by production code, no hardcoded classifications, no canned responses. If you find yourself writing a stub "just to get the demo working," stop — wire the real thing or cut the feature from the README.
- **DataHub is a startup requirement.** `airlock serve` must fail fast — with a named error and the exact fix — if it cannot compile a policy snapshot from a live DataHub. There is no code path that decides without the graph. Any PR that introduces one is rejected regardless of what it enables.
- **Fakes live only under `tests/unit/`**, behind the same protocols the real implementations satisfy. Integration tests and the demo run against the real DataHub quickstart and a real DuckDB file. The demo *is* an integration test that happens to be watchable.
- **Prove it's real in the demo:** the live-retag moment (change a tag in the DataHub UI → enforcement changes on next refresh) is scripted in `demo/SCRIPT.md` and must always work. It is the single most convincing thirty seconds we have.

## 11. Runs on any machine

Judges own arbitrary laptops. Cross-platform is a correctness requirement, enforced mechanically:

- **Universal-wheel rule:** a dependency may be added only if prebuilt wheels exist for macOS (arm64 + x86-64), Linux (x86-64 + arm64), and Windows on our Python versions. Check before adding; no dependency that triggers a source build on any platform, ever.
- **No POSIX-only anything in the judge path.** The launcher is `python demo/up.py` (stdlib + `docker compose` via subprocess), not a shell script. No `fcntl`, no Unix-socket assumptions, no hardcoded `/tmp`; `pathlib` for every path; `encoding="utf-8"` explicit on every `open()`; `uvloop` is an optional accelerator that is absent on Windows, never a requirement.
- **CI matrix:** {ubuntu, macos, windows} × {3.11, 3.12}. The matrix runs unit tests everywhere and *boots the full demo stack* everywhere. A platform-specific failure blocks merge exactly like a test failure.
- **Idempotency rule:** every setup-path command (`up.py`, `init`, `reset.py`, seed scripts) must be safe to run twice. Second run detects existing state and converges, never errors, never duplicates data.

## 12. Concurrency, performance, and production readiness

- **Async discipline:** the MCP layer is asyncio end-to-end. No blocking I/O in the event loop — warehouse calls go through pooled connections via `asyncio.to_thread` or a native async driver. Every `await` that can hang carries a timeout. `ruff`'s async lints (`ASYNC` rules) are enabled and blocking.
- **Snapshot pinning:** each request captures the current `PolicyGraph` reference at ingress and uses it for its whole lifetime; refresh swaps an atomic reference. No locks on the read path, no torn policy reads. (Frozen dataclasses per §7 make violations loud.)
- **Decision cache + coalescing:** memoize verdicts on `(sql, principal, snapshot_hash)`; coalesce identical in-flight queries per principal (singleflight). Both must have tests covering invalidation-on-snapshot-change and the double-send case — a cache that survives a policy change is a security bug, not a perf feature.
- **Cancellation propagates:** client disconnect → cancel the warehouse statement → return the connection. Test with a client that drops mid-query.
- **Budgets are CI gates** (`make bench`, `make load`): decision p95 < 10 ms; cache-hit p95 < 1 ms; 50 sustained concurrent principals with zero errors; 200-burst handled by the bounded queue with clean `AIRLOCK-440` rejections above the cap. Numbers land in `docs/benchmarks.md`; a regression fails the build.
- **Ops surface:** `/healthz`, `/readyz` (ready ⇔ valid snapshot loaded), graceful shutdown with a drain deadline, `airlock doctor`. All four exist before the first demo recording.
- **The zero-traceback rule:** during `make judge`, no unhandled traceback may reach stdout, stderr, or any MCP response. One traceback = P0, fix before anything else.
- **`make judge` — the hostile-user gauntlet.** An automated suite replaying everything a judge might do: concurrency burst, identical double-sends, the malformed-SQL corpus, natural-language input, kill-and-restart of the DataHub container mid-run, warehouse connection drops, `up.py` re-runs, Ctrl+C mid-query with restart. Green on all three OSes is a release precondition and the final rehearsal before recording the video. When someone reports "I did X and it broke," X becomes a new gauntlet case in the same PR as the fix.

## 13. Scope guard — what to build, in order, and what to refuse

Build order (do not reorder): 1) analyzer resolve+rewrite with mask/deny on DuckDB, 2) PolicyGraph compilation from DataHub (with the fail-fast startup requirement from §10), 3) MCP layer + envelopes on the async foundation from §12, 4) substitution via lineage, 5) audit JSONL + DataHub write-back, 6) CLI (`init`, `check`, `tail`, `serve`, `doctor`) + `/healthz` `/readyz`, 7) cross-platform demo stack (`demo/up.py`, `demo/reset.py`, seed, `SCRIPT.md`) + `examples/`, 8) `make judge` gauntlet green on all three OSes, 9) monitor mode, 10) Postgres adapter, 11) OTel.

Refuse, even if it seems quick: row-level security, result-set DLP scanners, a web dashboard, Snowflake before the demo works, wrap-mode for arbitrary MCP servers, any LLM call inside Airlock itself (the gateway is deterministic — that determinism is a feature we advertise; do not compromise it).

When in doubt, optimize for the judge's five minutes: clean clone → `./demo/up.sh` → scripted prompts → visible verdicts → visible write-back in the DataHub UI. Anything that doesn't survive that path doesn't matter.
